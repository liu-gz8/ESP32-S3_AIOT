# WiFi 上报 与 USB(OTG)升级 可行性分析

> 依据:`esp32-s3_datasheet_cn.pdf`(USB PHY 与管脚约束)、本机 ESP-IDF 6.1.0 组件清单(已核查)。
> 关联:`docs/硬件v2引脚分配表.md`、`docs/双模AI识别架构设计.md`。

## 一、结论速览

| 能力 | 可行性 | 关键约束/代价 |
|---|---|---|
| WiFi 上报(音频片段/识别结果) | ✅ 可行 | 功耗(发射峰值 300mA+)、与摄像头/ESP-SR 的 CPU/PSRAM 竞争、需分区表支持 |
| WiFi OTA 升级 | ✅ 可行(推荐主路径) | 需要双 OTA 分区(16MB Flash 足够) |
| USB 升级:ROM 下载模式(esptool) | ✅ 可行 | 不需写任何 USB 代码,即现在用的烧录方式 |
| USB-OTG 设备(MSC 拖拽/DFU) | ⚠️ 有条件可行 | **USB-OTG 与 USB 串口/JTAG 共用内部 PHY(GPIO19/20),不能同时使用**;需时间复用或外接 PHY,且需要额外组件 |

## 二、WiFi 上报可行性

### 2.1 数据量与带宽(不是瓶颈)

| 数据 | 计算 | 结论 |
|---|---|---|
| 16kHz / 16bit / 单声道 PCM | 32KB/s(256kbps) | 一段 2 秒语音约 64KB |
| WiFi TCP 实测吞吐 | 通常 ≥1~2Mbps | 传一段 2 秒语音约 0.3~0.5s |

**带宽完全够用,主要矛盾在功耗与共存**。

### 2.2 共存与资源

| 项目 | 影响 | 对策 |
|---|---|---|
| WiFi 与 ADC2 | 手册明确:**ADC2 不能与 WiFi 同时使用** | 本项目不使用 ADC2,无影响(也是电池检测不能走 ADC 的原因) |
| WiFi 与摄像头/视觉推理 | 争 CPU 与 PSRAM 带宽 | 上报与视觉推理错峰;双核分工 |
| WiFi 与 ESP-SR | 争 CPU | 音频/ESP-SR 固定 Core 1,WiFi/视觉在 Core 0 |
| WiFi 缓冲内存 | 占用内部 RAM | 音频缓冲放 PSRAM,减少内部 RAM 压力 |
| 功耗 | 发射峰值 300mA+,平均随占空比 | 攒批上报 + 占空比调度;必要时只在联网时开 WiFi |

### 2.3 软件设计要点

1. **协议选择**:MQTT(常连、适合小报文)或 HTTPS 上报(简单、无状态);音频文件可用 HTTP POST;
2. **配网**:首次使用需 WiFi 配网(SmartConfig / BLE 配网 / 串口下发),账号密码存 NVS;
3. **断网缓冲**:无网时把片段写入 flash(或 SD),恢复后补传(需要 storage 分区);
4. **安全**:HTTPS 需根证书;敏感数据(人脸特征/录音)建议加密或仅在本地处理;
5. **省流**:语音可用 ADPCM/OPUS 压缩后再传(可选,占 CPU)。

## 三、USB(OTG)升级可行性

### 3.1 关键约束:两个 USB 控制器共用同一对 PHY 引脚

ESP32-S3 手册说明:USB 串口/JTAG 控制器与 USB OTG 控制器**连接内部 PHY 时都使用 USB_D-/USB_D+(GPIO19/20)**,两个外设可通过**时分复用**共用,或各选不同 PHY(需外接 PHY)。

对本项目的直接影响:

- 我们的引脚方案把**日志/调试放在 USB 串口/JTAG** 上(因为释放了 43/44);
- 因此 **USB-OTG 设备模式(MSC/DFU)不能在运行期与它同时工作**;
- 若要同时具备,只能:① 时间复用(切换控制器,复杂);② 给 OTG 外接 PHY(增加 BOM 与走线);③ 把日志改回 UART0(占用 43/44)。

### 3.2 四种升级路径对比

| 路径 | 需要什么 | 对现有方案的影响 | 评价 |
|---|---|---|---|
| **A. ROM 下载模式(esptool)** | USB 串口/JTAG + BOOT 脚(现有) | 无影响 | ✅ 开发/产线首选,零代码 |
| **B. WiFi OTA(esp_https_ota)** | 双 OTA 分区 + 服务器 | 需改分区表 | ✅ 现场升级首选 |
| C. USB-OTG MSC(拖拽 .bin) | USB 设备栈组件 + FAT 分区 + 自定义逻辑 | 与 USB 串口/JTAG 冲突 | ⚠️ 体验好但要额外设计 |
| D. USB-OTG DFU | USB 设备栈组件(DFU 类) | 同上 | ⚠️ 同上,且依赖组件可用性 |

组件现状(本机 IDF 6.1.0 已核查):

- 已有:`esp_driver_usb_serial_jtag`、`esp_hal_usb`、`esp_usb_cdc_rom_console`;
- **未内置** USB 设备栈(MSC/DFU 类实现),需要从组件库拉取(需联网);
- OTA 相关已具备:`app_update`、`esp_https_ota`。

### 3.3 推荐组合

1. **开发与产线**:路径 A(USB 串口/JTAG + esptool),零额外成本;
2. **现场升级(主)**:路径 B(WiFi OTA),配合双 OTA 分区;
3. **现场升级(备)**:路径 A(插 USB + 复位进下载模式);
4. **MSC 拖拽**:仅在明确需要"U 盘式升级"时再做,并接受 ①外接 PHY 或 ②日志改回 UART 的代价。

## 四、分区表规划(16MB Flash,支持 OTA)

现有 sdkconfig 使用单应用分区表(`factory 1M`),**不满足 OTA**,需要自定义 `partitions.csv`:

```csv
# Name,   Type, SubType, Offset,   Size, Flags
nvs,       data, nvs,     0x9000,   0x6000,
otadata,   data, ota,     0xf000,   0x2000,
phy_init,  data, phy,     0x11000,  0x1000,
ota_0,     app,  ota_0,   0x20000,  0x400000,
ota_1,     app,  ota_1,   0x420000, 0x400000,
model,     data, spiffs,  0x820000, 0x400000,
storage,   data, spiffs,  0xc20000, 0x3e0000,
```

| 分区 | 大小 | 用途 |
|---|---|---|
| ota_0 / ota_1 | 各 4MB | 双镜像,支持回滚 |
| model | 4MB | ESP-SR / 人脸模型文件(独立于固件,可单独更新) |
| storage | 约 3.9MB | 断网缓存的音频片段、人脸库、日志 |

注意事项:

- 应用固件必须 < 4MB(含 ESP-SR 与视觉库后需实测);
- 模型放独立分区,便于 OTA 只更新模型;
- 改分区表后需重新烧录并 `pio run -t erase` 清理旧数据。

## 五、风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| WiFi 发射与视觉推理抢资源 | 卡顿/丢帧 | 双核分工 + 错峰;关键路径优先级提升 |
| 上传耗电 | 续航下降 | 攒批上传 + 占空比;非必要时关 WiFi |
| OTA 失败变砖 | 设备不可用 | 双分区 + 回滚;保留 USB 下载兜底 |
| USB 控制器冲突 | 无法同时用调试与 OTG | 明确取舍:日志走 USB 或 OTG 走 USB |
| 16MB 分区拥挤 | 模型/应用放不下 | 模型独立分区 + 按需裁剪 |
