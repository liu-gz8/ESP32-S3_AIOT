## 二、验证方法

```
烧录固件 → 串口落盘抓取 → 复位拿开机日志 → 喊"你好小智"
         → 听提示音 → 停 5s → 说"打开电灯" → 分析日志
```

关键点是**先开抓取再复位**:复位那一下会把开机日志打出来,错过就得再复位一次。

## 三、开机日志确认的三件事

```text
I (3045) speech: MultiNet: mn7_cn, 每次 512 点, 采样率 16000 Hz
I (3065) MN_COMMAND: Command ID1, phrase ID0: da kai dian deng
I (3065) MN_COMMAND: Command ID2, phrase ID1: da kai fang men
I (3105) speech: feed=1024 点/通道 * 2 通道, fetch = 512 点, 采样率 = 16000Hz
I (3105) speech: PSRAM: 7716 KB -> 4271 KB(AFE占用 3445 KB)
```

1. **MultiNet 要求每次喂 `get_samp_chunksize()` 个样本**,实测 `mn7_cn` 是 512 点,
   和 AFE 的 fetch 输出长度完全一致。所以"拿 `res->data` 直接喂 `detect()`"是对的,
   不需要再做分帧适配。这一条先确认下来,后面识别不中就不用怀疑分帧了。
2. 两条命令词的拼音都被声学集合接受,`esp_mn_commands_update()` 没有回错误链表。
3. AFE 的 PSRAM 占用从接入 WakeNet 时的 1239KB 涨到 3445KB。命令词模型的代价不小,
   剩余 4271KB——后面加视觉模型时这笔账要先算。

```text
I (50075) speech: 唤醒已关闭（半双工）
I (50405) speech: 唤醒命中:word = 1 , model = 1, len = 15853
I (52605) speech: 识别到命令: id = 1, 文本 =  da kai dian deng
```

两个顺带印证的细节:

- `唤醒已关闭` 和 `唤醒命中` 之间固定差 **330ms**,就是 `wake.pcm` 那 0.32 秒的**阻塞播放**。
  日志顺序看着别扭(先"关闭"后"命中"),是因为 `speech_set_wakenet(false)` 和播报都在
  `ESP_LOGI("唤醒命中")` 之前执行。
- 命令是在唤醒后 2.2 秒被识别的,远在 5 秒窗口内,窗口长度是合适的。

## 五、取证过程踩的坑(工具层面)

这一节和固件无关,但下次抓日志会省很多时间。

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 复位后串口日志停在 9.5 秒不再增长 | ESP32-S3 的 USB-Serial/JTAG 在芯片复位时会**重新枚举 USB**,已打开的串口句柄失效,`ReadExisting()` 抛异常被 `catch` 吞掉,循环空转 | 长时抓取**不要中途复位**;需要开机日志时,先开抓取再复位,或在复位后重开连接 |
| 2 | `pio device monitor` 按 Ctrl+C / 菜单键都退不掉 | 监视器在 PTY 下不转发控制字符 | 直接 `Stop-Process` 掉 `pio.exe` 及其 python 子进程,再重启抓取 |
| 3 | 中文日志全是 `??????` | 串口按默认编码解码 | 设 `$cap.Encoding = UTF8`,文件用 `UTF8Encoding($false)` 写 |

最终方案:用 PowerShell 开 `System.IO.Ports.SerialPort`,25ms 轮询 `ReadExisting()`,
带时间上限地写进文件再退出。比交互式监视器更适合"跑一次、离线慢慢查"的场景。

## 六、丢块对账(本日最有价值的一段)

链路里有**两个计数器**:`audio_app_task` 的 `blk=`(每块自增)和 `speech` 任务收到的
`收到 N 块`。两者本该同步,实际却对不上:

| `收到 N 块` | `blk=` | 差值 |
|---|---|---|
| 500 | 500 | 0 |
| 2000 | 2000 | 0 |
| 2500 | 2610 | **110** |
| 3000 | 3230 | **230** |
| 5500 | 5740 | 240 |
| 6950 | 7190 | 240 |

差值在 2000 块之前是 0,到 2500 块跳到 110,3000 块到 230,之后 45 秒**一直稳定在 240 不再增长**。

再算"50 块的实际间隔"(正常应为 800ms),异常点只有两个,而且精确落在命令窗口结束、
`唤醒已开启` 的那一瞬间:

| 收块时刻 | 50 块间隔 | 正常值 |
|---|---|---|
| t=45285ms | **2700ms** | 800ms |
| t=54695ms | **2630ms** | 800ms |

### 机制

正常丢 800ms 的活,在某两次卡顿里花了 2.7 秒,即多停了约 1.9 秒。这 1.9 秒里
采集侧继续以 16ms/块投递,8 块队列(128ms)填满后,后续投递全部失败——按 1.9s 算
正好约 110 块,和实测的 110、120 两笔完全吻合。两次合计 240 块 ≈ 3.8 秒 ≈ 4% 的音频。

丢块之所以完全**无声**,是因为 `speech_push_pcm()` 在队列满时返回 `ESP_ERR_NO_MEM`,
而调用方没有接收返回值,也没有计数:

```c
speech_push_pcm(pcm, RX_FRAME_COUNT);   /* 返回值被丢弃 */
```

嫌疑最大的是 `speech_set_wakenet(true)` 里的 `reset_buffer()` + `enable_wakenet()`
这一段。但为什么只有前两次唤醒后卡顿、后两次没有,目前还只是猜测——要定论得加一行计时。

另外还看到 2 次 `W AFE: Ringbuffer of AFE is empty`,位置和上面的卡顿点重合,
是同一个现象的另一面。

## 八、经验

1. **阻塞式播放会把整条流水线的节奏带偏**:播报 0.32s 期间采集侧不投递,而恢复瞬间
   又正好是"重开唤醒"的卡点,两者叠加就是丢块的高发区。
2. **"队列满即丢"的接口必须回报失败**:这次为了定位 240 个块的去向绕了一圈,
   根因就是返回值被忽略、失败无声。可观测性本身就是功能的一部分。
3. **计数对账是最便宜的定位手段**:两个计数器一相减,问题就从"感觉有丢"变成
   "在 45 秒处丢了 110 块"。不需要示波器,也不需要猜。
4. **先确认参数再谈调优**:MultiNet 的 512 点和 AFE 的 512 点对上之后,
   "识别不中"这类问题就可以直接排除分帧这个方向了。
5. **复位会断 USB 枚举**,这是 USB-Serial/JTAG 方案的固有行为,不是板子坏了。
