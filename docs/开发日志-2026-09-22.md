## 二、为什么要删掉自研 VAD

自研 VAD 是"能量 + 自适应噪声底 + 双门限"那一套。它在两类场景会失效:非平稳噪声
(音乐、键盘、旁人说话)一响就被当成语音;信噪比低时又判不出来。实测那 97 秒里
只说了 4 句话却切出 20 个片段,就是它在原始双麦音频上被噪声牵着走的结果。

换到 AFE 之后,判决依据从"声音响不响"变成"像不像人声"(VAD 跑在 SE 增强后的音频上),
而且**迟滞参数由 AFE 管**:`vad_min_speech_ms`(默认 128ms)代替了原来的
`VAD_ONSET_FRAME 3`, `vad_min_noise_ms`(默认 1000ms)代替了 `VAD_OFFSET_FRAME 18`。

代价是可调性下降——VadNet 是黑盒,以后遇到特殊噪声场景只能调阈值,不能改算法。
`vad.c` 有提交记录,需要时可以 `git restore` 拿回来对比。

## 三、职责边界重划

```text
你的代码                          AFE 框架
  I2S 采集(32bit 槽, 立体声)        SE(BSS) 双麦增强
  解码(>>16 → int16 交错立体声)      VAD
  speech_feed_pcm() ──feed──>      WakeNet
  <──fetch── 干净单声道 + vad_state
  边沿检测 → 片段池                  (MultiNet 不在 AFE 里)
  命令词: s_mn->detect()
  播报: audio_out_task
```

**MultiNet 不在 AFE 流水线里**——AFE 的流水线只有 `SE → VAD → WakeNet` 三级,
命令词是在 fetch 之后由自己的代码调 `s_mn->detect(res->data)`。

## 四、今天最有价值的发现:2000ms 是 fetch 的内建超时

09-21 遗留的"2.7 秒卡顿"今天定位到了根因,写在 `esp_afe_sr_iface.h` 的注释里:

```c
 * @Warning  The output is single channel data, no matter how many channels the input is.
 *           Timeout is 2000 ms. If you want to adjust timeout, please refer to the
 *           definition of `fetch_with_delay`.
```

实测 `fetch 阻塞 1996 ms` / `2005 ms`,就是这个硬编码值。它之所以会打满,是因为
**唯一能给 AFE 灌数据的任务,当时正卡在 `fetch()` 里等它出帧**——互相等,只能靠超时解开。

两条实测数据顺手否掉了一个错误方向:`ret_value` 在**正常帧**上也是 `-1`,不能拿它
判断超时;真正的区分办法是用 `fetch_with_delay()` 自定义超时,或者看耗时。

拆分 feed/fetch 之后,这个问题从结构上消失了——采集任务在 `rb_in` 变空之前就会补上。

## 五、播报阻塞 fetch 引发的一串警告

改完之后出现过 `Ringbuffer of AFE(FEED) is full` 三连警告:

```text
7303  唤醒已关闭（半双工）   ← 开始播提示音
7483  FEED full              ← 180ms 后输入环就满了
7543  FEED full
7603  FEED full
```

链条是: `audio_out_play_file()` 是**阻塞**的(同步写 DMA + 尾部静音),它跑在
`speech_fetch_task` 里 → 这 320ms 内 `fetch()` 一次没调 → 输出环 `rb_out` 满 →
`afe_mase` 写不进去被卡 → 输入环 `rb_in` 没人消费 → 采集侧还在 64ms 一块地灌 →
溢出丢数据。

修法两件事**缺一不可**:

1. **播报独立成任务**(`audio_out_task` + 请求队列),`audio_out_play_file()` 只投递
   不等待,`fetch` 循环不再被阻塞;
2. **采集侧保留半双工检查**(`if (audio_out_is_playing()) continue;`)——这一条防的是
   提示音被麦克风拾到后灌进 AFE。任务拆分解决不了这个,因为拆分后 `fetch` 一直在跑,
   提示音会照常被 MultiNet 处理。

## 六、片段池的两个改动

**数据源简化**:原来收立体声后在内部 `(L+R)/2` 下混,还额外开了一个
`int16_t mix_buf[RX_FRAME_COUNT]` 在栈上。现在 AFE 输出的本来就是 SE 增强后的
单声道,下混和 `mix_buf` 都删掉了,`peak_l/peak_r` 合成一个 `peak`。

**补头二选一**:改成 `audio_segment_feed()` 接收外部的补头参数,rising 时
有外部补头就用它、没有才倒自己的 pre-roll。实测日志:

```text
AUDIO_SEG: 补头来源: AFE vad_cache
```

说明 `vad_cache` 确实非空,补头这件事 AFE 包了,自研 pre-roll(300ms / 9600B)只作兜底。

顺带修掉一个隐患:原来那句独立的 cache 调用硬传 `is_speech = true`,只要某帧静音时
`vad_cache_size` 非 0,就会在静音里凭空起一个片段。改完之后 cache 只在 rising 分支
被读取,和状态判断解耦了。

## 七、踩过的坑

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 命令词永远识别不到,每次都是"命令窗口超时" | 命令窗口那个 `if` 被误嵌进 `if(res->wakeup_state == WAKENET_DETECTED)` 里面,而 `wakeup_state` 只在唤醒词那一帧才是 DETECTED | 把命令窗口整块挪到唤醒分支**外面**,和它平级 |
| 2 | 一启动就断言崩溃 | `s_pcm_q` 删了,但 `speech_set_wakenet()` 里的 `xQueueReset(s_pcm_q)` 没删 → 对 NULL 队列操作 | 声明和调用一起删 |
| 3 | `calloc` 申请了 4MB | `calloc(PCM_16_FRAMES, PCM_16_BUFFER_BYTES)` = 1024 × 4096 | 第二个参数应为 `PCM_16_BYTES_PER_FRAME`(1024 × 4 = 4KB) |
| 4 | 片段永远不闭合,池子借出就回不来 | 静音帧被 `continue` 滤掉,`falling` 边沿永远检测不到 | 静音帧必须照样喂进池子,由池子自己决定要不要 append |
| 5 | 唤醒功能失效 | `speech_feed_pcm()` 末尾多了一行 `speech_set_wakenet(false)` | 删掉——它会让唤醒词每秒被关 60 多次 |

## 八、关键数据

| 指标 | 数值 |
|---|---|
| 采集块 | 1024 帧 = 64ms |
| AFE feed → fetch | 1024 点/通道 ×2 → 512 点 |
| 唤醒命中 → 命令识别 | 约 2.3s |

## 九、经验

1. **接口的方向要看签名**:`feed(afe, const int16_t *in)` 有音频参数,所以它是入口;
   `fetch(afe)` 只有句柄,所以它是出口。把"给 fetch 喂音频"这种方向记错,后面所有
   设计都会跟着歪。
2. **阻塞式调用放在实时循环里,一定会以别的形式还回来**:播报阻塞 fetch → 输出环满 →
   输入环溢出。拆任务比调超时值更根本。
3. **定长接口不能用"有多大传多大"的直觉去用**:`feed()` 无条件按 `aec_frame_size`
   往后读,少传就是越界读。攒够 1024 点是接口要求,不是设计选择。
4. **先观测再下结论**:`ret_value = -1` 差点被当成超时标记,打一次正常帧的日志就否掉了。
   今天两次"以为"都被一行日志推翻。
5. **删接口要连调用点一起删**:`s_pcm_q` 的教训——删了队列却留了 `xQueueReset`,
   编译能过,一跑就崩。
