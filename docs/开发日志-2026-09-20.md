## 二、为什么要拆:一个"永远追不上"的时间轴

拆分前的结构是"采集任务里直接调 `speech_feed()`",而 `speech_feed()` 内部有**阻塞式 `fetch()`**:

```
|<----- 64ms 音频(4 个采集块) ----->|<-- 等 AFE 出帧 ~32ms -->|
                                    ^feed        ^fetch 阻塞返回
一个周期 ≈ 96ms > 64ms 音频
```

这 32ms 的等待是加在 64ms 音频周期**之外**的串行开销,采集任务在等 AFE 的时候不读 I2S,
DMA 缓冲填满后就丢数据。实测:

| 指标 | 拆分前 |
|---|---|
| 采集实际速率 | 实时的约 **61%**(丢约 40% 麦克风音频) |
| feed 被拒 | 2048 次里被拒 **1022 次** |
| 产出 / 实际 | 65.5s / 143s |

## 三、新结构

```
audio_app_task (核0)                speech_task (核1, 优先级4, 栈8KB)
  I2S 读 2048B                         xQueueReceive(portMAX_DELAY)
  解码 / RMS / VAD / 片段         <──  攒够 1024 点 → feed
  speech_push_pcm(0 超时,满即丢) ──>  按比例 fetch(1 次 feed 出 2 帧)
                                       → 输出帧缓存/唤醒事件
```

| 任务 | 核 | 优先级 | 栈 | 职责 |
|---|---|---|---|---|
| `audio_app_task` | 0 | 5 | 4096 | 采集、解码、RMS、VAD、片段 |
| `speech` | 1 | 4 | 8192 | AFE 攒帧、feed/fetch、唤醒事件 |
| `seg_consumer` | 未绑 | 4 | 4096 | 片段消费者 |
| `perf`(临时) | 0 | 1 | 4096 | 每 5 秒打印运行时统计,调试完已注释 |

关键设计点:

1. 队列项是**固定块长**(256 帧立体声 = 1024 字节),深度 8 = 128ms 抖动余量;
2. 投递侧用 `xQueueSend(..., 0)`,**绝不阻塞采集**——队列满说明识别侧没跟上,丢新块而不是拖住 I2S;
3. 一次 feed 对应 2 帧输出(输入 1024 点/通道,输出 512 点),必须按比例取够;
4. 拆完之后,`fetch()` 里跑的 WakeNet 推理不再占用采集任务的栈,顺带解决了 4KB 栈跑深调用链的隐患。

## 四、任务看门狗排查:从现象到定位

### 4.1 现象

```
E task_wdt: Task watchdog got triggered ...
E task_wdt:  - IDLE1 (CPU 1)
E task_wdt: CPU 1: speech
```

Task WDT 监测的是 **IDLE 任务**(`CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1`),IDLE 只有在同核其它任务
全部阻塞时才能运行。所以这条报错的含义是:**core 1 上有个任务连续 5 秒没有阻塞过**——不是"没喂狗"。

用 `addr2line` 解 backtrace,落在 `afe_fetch → afe_wn_run_multi_mic → WakeNet 推理 → conv2d`,
说明任务确实在跑真实的 DSP 与推理,不是死循环。

### 4.2 打开运行时统计

```
CONFIG_FREERTOS_USE_TRACE_FACILITY=y
CONFIG_FREERTOS_USE_STATS_FORMATTING_FUNCTIONS=y
CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y
CONFIG_FREERTOS_RUN_TIME_STATS_USING_ESP_TIMER=y
CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID=y
```

读表要点:**百分比的分母是墙上时间**,不是所有任务时间之和,所以加起来会超过 100%;
每个任务的百分比就是"占一个核的比例",而一个任务跑满一个核 ≈ 100%。

### 4.3 两轮数据对比

| 任务 | 降负载前 | 降负载后 |
|---|---|---|
| `speech` | **82%** | **43%** |
| `IDLE1`(core1 空闲) | 6% | 52% |
| `IDLE0`(core0 空闲) | 89% | 44% |
| `audio_app_task` | 3% | 1% |

降负载的两个动作:

1. `cfg->ns_init = false`(关掉降噪);
2. `cfg->memory_alloc_mode = AFE_MEMORY_ALLOC_INTERNAL_PSRAM_BALANCE`(张量优先放内部 RAM)。

### 4.4 结论

**这个双麦版 AFE 没有独立任务**,DSP 和唤醒词推理都在 `fetch()` 的调用者上下文里执行,
所以 `speech` 任务的优先级/绑核,就是整个音频前端的优先级/绑核。这也解释了为什么
"把采集任务绑到 core 0"和"改内存策略"单独做都没效果——真正的负载在 `speech` 里。

## 五、唤醒应答闭环:三个机制缺一不可

唤醒后播报应答提示音的流程:

```
唤醒命中 → speech_set_wakenet(false) → 播 /spiffs/wake.pcm → reset_buffer + xQueueReset → 重新开启唤醒
```

| 机制 | 防的问题 |
|---|---|
| 半双工(播放期间 `disable_wakenet`) | 自己的提示音把自己唤醒 |
| `reset_buffer` + `xQueueReset(s_pcm_q)` | 播放期间/播放前残留的音频在重启唤醒后被重新喂入而自触发 |
| 2 秒节流 | 一句话被判定成多次(WakeNet 逐帧滑窗,会连续多帧报命中),导致提示音连播 |

缺任何一个都会表现成"误触发"。

## 八、经验

1. **生产者/消费者模型里,出错路径上跳过的动作往往正是维持平衡的动作**:`feed()` 被拒时
   如果 `continue` 跳过 `fetch()`,缓冲区就永远排不空,一次拒绝变永久死锁;
2. **喂与取要按比例配对**:喂 64ms 就要取够 64ms 的输出,取少了输出环积压会把上游堵死;
3. **先观测再调参**:两轮 runtime stats 就把"谁占 CPU"从猜测变成了数据;
4. **任务 WDT 报 IDLE = 同核任务不阻塞**,不要用 `esp_task_wdt_reset()` 去糊;
5. **禁用调试级堆功能**(poisoning / task tracking)在接入大模型后是必须的,否则初始化会被拖到
   触发超时(这一条在 21 日凌晨的 MultiNet 接入中应验,详见次日日志)。
