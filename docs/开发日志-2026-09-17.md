## 二、为什么用组件管理器接入

ESP-SR 的核心(C 源码 + 预编译库 + 模型)体积很大,用 IDF 组件管理器比手工拷贝干净:

| 文件 | 作用 | 是否提交 |
|---|---|---|
| src/idf_component.yml | 声明依赖 espressif/esp-sr ^2.5.3 | 提交 |
| dependencies.lock | 锁定每个组件的精确版本与哈希 | 提交 |
| managed_components/ | 实际下载的代码(约 380MB) | 不提交(已在 .gitignore) |

实际拉到的组件:esp-sr 2.5.3、esp-dl 3.3.11、esp-dsp 1.8.0、dl_fft 0.7.0、cjson 1.7.19、esp_new_jpeg 1.0.2。
其中 **esp-dl 后面做视觉时可以直接复用**。

版本选择依据:esp-sr 2.5.0 的 CHANGELOG 明确写了"Resolve the incompatibility between Kconfig and IDF v6.1",
与本工程的 IDF 6.1.0 正好对上。

## 三、模型选型与配置

### 3.1 选型

| 用途 | 模型 | 体积 | 备注 |
|---|---|---|---|
| 唤醒 | wn10_nihaoxiaozhi | 777KB | WakeNet10,q16 权重;_MODEL_INFO_ 里阈值 0.5831/0.5959 |
| 命令词 | mn7_cn | 2609KB | MultiNet7,比 mn6 更小更快(2.92MB/11ms vs 4.1MB/12ms) |

### 3.2 关掉多余的唤醒词

中途 sdkconfig 里被打开了三个唤醒词(wn9s_nihaoxiaozhi、wn9_xiaobinxiaobin_tts),后果有两个:

1. srmodels.bin 从 3.32MB 涨到 3.89MB,model 分区只剩 194KB 余量;
2. AFE 会为每个唤醒词分配 model index,**第二个模型在误触发**(日志里出现 model = 2)。

已改为只保留 wn10_nihaoxiaozhi。以后要加第二个唤醒词,正确做法是用 cfg->wakenet_model_name_2 明确指定,
而不是往包里多打几个模型。

### 3.3 两处容易踩的配置

- **sdkconfig 优先级高于 sdkconfig.defaults**:只改 defaults 不生效,两边要同步改;
- **主频 160MHz 提到 240MHz**:按官方基准,双麦 AFE(47%)+ WakeNet10(22.6%)常开约占单核 70%,
  160MHz 下换算成 105%,跑不动。

## 四、模型分区:打包与烧录

ESP-SR 原本依赖 IDF 的 flash 目标烧模型,而 PlatformIO 用自己的 upload 流程,不会执行 IDF 的自定义 ALL 目标,
所以模型不会自动生成。解决方案是写一个 extra_script:

1. 构建结束:调 movemodel.py,按 sdkconfig 选型打包出 srmodels.bin;
2. 烧录时:把 srmodels.bin 追加进 UPLOADERFLAGS,写到 partitions.csv 里的 model 分区。

两个关键点:

1. movemodel.py 会**先删掉 build/srmodels/ 再重新拷**,不会累积重复模型;
2. extra_scripts 的执行时机在平台脚本**之后**,那时 UPLOADERFLAGS 已经拼好了,
   所以追加 FLASH_EXTRA_IMAGES 无效,**必须直接改 UPLOADERFLAGS**。

## 五、speech 模块设计

### 5.1 初始化序列

```
esp_srmodel_init("model")                挂载模型分区
afe_config_init("MM", models, AFE_TYPE_SR, AFE_MODE_LOW_COST)
  - aec_init = false      半双工,没有回采通道
  - se_init  = true       双麦增强
  - ns_init / vad_init    先用 WebRTC
  - wakenet_init + 按名字精确挑 wn10_nihaoxiaozhi
  - afe_perferred_core = 1, priority = 5
  - memory_alloc_mode = MORE_PSRAM, ringbuf = 8 帧
esp_afe_handle_from_config(cfg) -> create_from_config(cfg) -> print_pipeline()
```

唤醒词不靠 esp_srmodel_filter 取"第一个 wn",而是按名字精确匹配——包里有多个唤醒词时,
谁排在前面取决于目录名字母序,不可控。

### 5.2 数据流

| 参数 | 实测值 | 含义 |
|---|---|---|
| 采集块 | 256 点/块(16ms) | I2S DMA 阻塞读 |
| feed_chunksize | 1024 点/通道(64ms) | 要攒 4 个采集块才喂一次 |
| fetch_chunksize | 512 点(32ms) | 单声道输出 |
| 比例 | 1 次 feed 出 2 帧输出 | 每次 feed 后按这个比例取帧 |

输出用 4 帧队列缓存,speech_take_frame() 每次交付一帧且只交付一次(带"新帧"语义)。

### 5.3 半双工

speech_set_wakenet(false/true):播放提示音前关唤醒,播完 reset_buffer + 开启,
并清空内部攒帧与输出队列——播放期间那段音频是回声,不能拿去判唤醒。

## 六、问题排查记录(本次最有价值的部分)

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 链接失败:multiple definition of vad_process | 自研 VAD 的 vad_process/vad_state_t 与 esp-sr 的 esp_vad.h 重名 | 自研符号统一加 app_ 前缀 |
| 2 | 一直刷 Ringbuffer of AFE(FEED) is full | feed() 被拒后用 continue 跳过了 fetch(),而 fetch 才是排空缓冲的动作,一次拒绝变永久死锁 | 无论 feed 成败都继续 fetch |
| 3 | 系统只能半速运行:2048 次 feed 被拒 1022 次,产出 65.5s / 实际 143s | 一次 feed 产出 2 帧输出,只取 1 帧,输出环积压导致 SE 任务停住,输入环随之灌满 | 按 feed_chunk/fetch_chunk 比例取帧 |
| 4 | 连续误唤醒(model = 2,len = 23265) | 盲取 3 次额外 fetch,在空环上重复跑唤醒判定;且包里多打了两个唤醒词模型 | 按比例精确取 + 关掉多余唤醒词 |
| 5 | 链接失败:undefined reference to seg_consumer_task | 片段消费者任务被删除,但 main.c 仍在创建 | 补回消费者(否则片段池 3 槽占满后全丢) |

问题 2 和 3 都源自同一个坑:**生产者/消费者模型里,出错路径上跳过的动作往往正是维持平衡的动作**。
问题 3 的定位方法值得记住——把"投入的音频时长 / 产出的音频时长 / 实际耗时"三个量打在一起,
2 倍失配一眼就能看出来。

另外,API 文档没写清的地方,managed_components/espressif__esp-sr/src/esp_afe_sr_1mic.ref 里有 AFE 的
**参考实现源码**,比文档可靠。

## 八、经验与教训

1. **出错路径要想清楚"谁因此失衡"**:continue 跳过 fetch 让缓冲永远排不空;
2. **生产者与消费者必须按比例配对**:喂 64ms 就要取够 64ms 的输出;
3. **第三方库引入后,自研符号要加前缀**,通用的 init/process/state_t 迟早撞车;
4. **日志频率会影响实时性**:115200 波特率下一行 70 字节约占 6ms,逐块打印会吃掉三分之一的循环时间;
5. 上层封装要提供"新数据"语义(speech_take_frame 返回 bool),只给"最新帧"会导致重复处理。
