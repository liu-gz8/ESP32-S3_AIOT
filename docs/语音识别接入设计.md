# 语音识别接入设计(选型 + 架构 + 里程碑)

> 前置状态:音频链路已完成(双麦采集 → 16bit 解码 → RMS → VAD → 片段缓冲)。
> 本文决定"音频交给谁识别",并给出对应的代码架构与实施步骤。

## 1. 两条路线

| | A. 本地识别(ESP-SR) | B. 边缘/云上行 |
|---|---|---|
| 识别内容 | 唤醒词 + 固定命令词 | 自由语音转文字 / 大模型 |
| 运行位置 | ESP32-S3 片内 | WiFi → 服务器/边缘盒子 |
| 网络依赖 | 无(离线可用) | 必须有网络与服务端 |
| 资源占用 | 模型占 flash/PSRAM,CPU 常驻推理 | 占用网络与上传带宽 |
| 延迟 | 低(数十~数百 ms) | 取决于网络,通常几百 ms 以上 |
| 现成支持 | 乐鑫 `esp-sr`(WakeNet + MultiNet) | 需自建服务端或用第三方 ASR |

**建议先做 A(ESP-SR)**,原因:

1. 不依赖服务器,闭环短,一个人就能做完;
2. 是"端侧 AI 部署"最典型的简历素材(唤醒词/命令词、内存与延迟优化);
3. 现有 16kHz 单声道 PCM 链路可以直接复用;
4. 以后要升级到 B,只需在"识别输出"这一层替换,不影响采集层。

## 2. 关键架构差异(决定代码怎么接)

### 2.1 ESP-SR 需要"连续音频流",不是"语音片段"

ESP-SR 的 AFE(音频前端)+ WakeNet(唤醒词)是**流式处理**:逐帧喂 16kHz 单声道 PCM,它内部自己做降噪、VAD 与唤醒判断。

- 正确接法:在 `audio_app_task` 里把下混后的 16k 单声道帧**每块都喂给 ESP-SR**;
- 错误接法:只把 `audio_segment` 产出的语音片段喂给它——中间会有断裂,唤醒词会被切坏。

### 2.2 那 `audio_segment` 还有用吗?有,分工如下

| 模块 | 职责 |
|---|---|
| 连续流 → ESP-SR | 负责"听到唤醒词"(常开,低延迟) |
| `audio_segment` | 负责"唤醒后的命令/录音片段"保存,用于上行、回放或二次识别 |

即:ESP-SR 管唤醒,VAD + 片段缓冲管"把命令段拿出来"。

## 3. 目标架构(A 路线)

```
mic 驱动(16k 立体声原始帧)
   ↓
audio_format:解码 + 下混 16k 单声道
   ↓                          ↓
ESP-SR(AFE + WakeNet)    VAD + audio_segment
   ↓ 唤醒事件                ↓ 命令片段
状态机(等待命令)  ←────────────┘
   ↓
动作/上报(串口、LED、网络)
```

## 4. 接口约定(建议)

```c
/* speech.h —— 识别层对外接口 */

typedef enum {
    SPEECH_EVT_NONE = 0,
    SPEECH_EVT_WAKE,        /* 唤醒词命中 */
    SPEECH_EVT_CMD,         /* 命令词命中(带命令 ID) */
} speech_event_t;

esp_err_t speech_init(void);                      /* 初始化 AFE/WakeNet/模型 */
speech_event_t speech_feed(const int16_t *mono,   /* 16k 单声道 PCM */
                           size_t frames);        /* 每 16ms 调用一次 */
```

调用位置:`audio_app_task` 里,下混得到 mono 之后:

```c
speech_event_t ev = speech_feed(mono, RX_FRAME_COUNT);
if (ev == SPEECH_EVT_WAKE)      { /* 进入命令等待态 */ }
if (ev == SPEECH_EVT_CMD)       { /* 执行动作 */ }
```

## 5. 里程碑与验收

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 | 添加 `esp-sr` 依赖,工程可编译(先不接逻辑) | 编译通过,固件体积记录 |
| M2 | 初始化 AFE + WakeNet,连续喂流 | 串口打印"喂流正常",无崩溃 |
| M3 | 唤醒词命中输出事件 | 喊唤醒词 → 打印 WAKE;安静 5 分钟误唤醒统计 |
| M4 | 接入命令词(MultiNet)或"唤醒后抓片段" | 喊命令 → 输出命令 ID / 片段 |
| M5 | 指标与优化 | 唤醒率、误唤醒次数、CPU/内存占用、响应延迟 |

注意:M2~M5 的**音频效果验收依赖稳定硬件**。当前原型接线不稳,建议:先把 M1 做完(纯编译),M2 之后等硬件 v2。

## 6. 资源与配置要求

- 采样率:16kHz、单声道、16bit(与现有链路一致);
- PSRAM:模型与运行缓冲需要外部 RAM(当前 8MB Octal PSRAM 已启用);
- Flash:16MB 已配置,建议后续为模型单独划分分区(便于 OTA 更新模型);
- 任务:ESP-SR 推理建议单独任务 + 适当优先级,避免阻塞采集;
- 现有调试开关:堆内存 poisoning 与任务跟踪会额外占用内存,接入 ESP-SR 后视情况关闭。

## 7. 风险与注意事项

1. **组件获取**:`esp-sr` 通过组件管理器拉取,需要网络(当前环境网络受限,需单独授权);
2. **模型选择**:WakeNet 有多套唤醒词模型(中文/英文,占用不同),MultiNet 命令词表需按需求裁剪;
3. **硬件依赖**:麦克风信噪比、双麦一致性直接影响唤醒率,需硬件 v2 稳定后评估;
4. **与 VAD 并存**:ESP-SR 自带 VAD,需避免与我们自研 VAD 冲突(建议:ESP-SR 负责唤醒,自研 VAD 负责命令段切分)。

## 8. 下一步动作

1. 确认路线(默认 A:ESP-SR);
2. M1:添加 `esp-sr` 依赖并跑通编译(需要网络授权);
3. 同时准备硬件 v2 引脚规划表(音频 + 摄像头 + PSRAM 预留),避免投板后返工;
4. 硬件 v2 到位后:恢复 VAD 标准素材复测 → M2~M5。
